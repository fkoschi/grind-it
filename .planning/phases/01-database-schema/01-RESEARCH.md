# Phase 1: Database Schema - Research

**Researched:** 2026-02-23
**Domain:** Drizzle ORM SQLite schema definition + Expo SQLite migrations
**Confidence:** HIGH

## Summary

Phase 1 adds two new SQLite tables (`machine_table` and `grinder_table`) to the existing Drizzle ORM schema and generates the corresponding migration (index 0009). The project already has a well-established pattern for this: define tables in `db/schema.ts` using `sqliteTable` from `drizzle-orm/sqlite-core`, run `npx drizzle-kit generate` to produce the SQL migration file and snapshot JSON, then register the new migration import in `drizzle/migrations.js`. The `DatabaseProvider` applies migrations automatically on app boot via the `useMigrations` hook.

The machine type system is a 14-value TypeScript const object stored as text in SQLite. This matches the existing pattern in the codebase where SQLite has no native enum support and text columns are the standard approach. The enum is purely a TypeScript-level constraint; SQLite stores the raw string.

**Primary recommendation:** Add the two table definitions to `db/schema.ts`, define the `MachineType` const object alongside them, run `npx drizzle-kit generate` to auto-produce the migration SQL + snapshot, and register the migration in `drizzle/migrations.js`. No new packages needed. No runtime code changes beyond the schema file and migration registration.

## Architecture Patterns

### Recommended Project Structure
```
db/
├── schema.ts              # ADD: machineTable, grinderTable, MachineType const
drizzle/
├── 0009_<generated_name>.sql   # AUTO-GENERATED by drizzle-kit
├── meta/
│   ├── 0009_snapshot.json      # AUTO-GENERATED by drizzle-kit
│   └── _journal.json           # AUTO-UPDATED by drizzle-kit
└── migrations.js               # MANUAL: add m0009 import + registration
```

### Pattern 1: SQLite Table Definition
**What:** Define tables using `sqliteTable` with column helpers from `drizzle-orm/sqlite-core`.
**When to use:** Every new table in the app.
**Example:**
```typescript
// Source: existing db/schema.ts pattern + Context7 drizzle-orm docs
import { int, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const machineTable = sqliteTable("machine_table", {
  id: int().primaryKey({ autoIncrement: true }),
  manufacturer: text().notNull(),
  name: text().notNull(),
  type: text().notNull(),
});
```

### Pattern 2: TypeScript Const Enum (No Native SQLite Enum)
**What:** Use a `const` object + type extraction for type-safe enums stored as text.
**When to use:** Any constrained string value in SQLite.
**Example:**

### Pattern 3: Migration Registration
**What:** After `drizzle-kit generate` produces a new SQL file, manually import and register it in `drizzle/migrations.js`.
**When to use:** Every time a new migration is generated.
**Example:**
```javascript
// Source: existing drizzle/migrations.js pattern
import m0009 from "./0009_<generated_name>.sql";

export default {
  journal,
  migrations: {
    // ... existing m0000-m0008 ...
    m0009,
  },
};
```

### Pattern 4: Integrated Grinder Types Array
**What:** Derive a constant array from `MachineType` that lists machine types with built-in grinders.
**When to use:** Phase 2+ UI logic that hides/shows the grinder section.
**Example:**
```typescript
export const INTEGRATED_GRINDER_TYPES: MachineType[] = [
  MachineType.SUPER_AUTOMATIC,
  MachineType.CAPSULE_POD,

```

### Anti-Patterns to Avoid
- **Hand-editing migration SQL files after generation:** The snapshot JSON must match the SQL exactly. If you need to change the schema, edit `db/schema.ts` and re-run `npx drizzle-kit generate`.
- **Adding runtime validation logic in Phase 1:** The schema phase only defines tables. Single-row enforcement, upsert logic, and form validation belong in Phase 2 (the hook/CRUD phase).
- **Using `integer({ mode: "boolean" })` or complex column modes:** Not needed for these tables. Keep columns simple: `int()` for id, `text()` for strings.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Migration SQL generation | Write CREATE TABLE SQL manually | `npx drizzle-kit generate` | Drizzle-kit generates the SQL, snapshot JSON, and updates the journal atomically. Hand-writing risks snapshot desync. |
| Migration application | Custom migration runner | `useMigrations(db, migrations)` hook from `drizzle-orm/expo-sqlite/migrator` | Already wired in `DatabaseProvider.tsx`. Zero additional work needed. |
| Enum validation at DB level | SQLite CHECK constraints | TypeScript const object + application-layer validation | SQLite CHECK constraints are not well-supported by Drizzle ORM's migration generator. TypeScript provides compile-time safety; runtime validation goes in the form (Phase 2). |

**Key insight:** The entire migration pipeline is already automated. The only manual step is registering the new import in `migrations.js`. Everything else (SQL generation, snapshot creation, journal update, runtime application) is handled by existing tooling.

## Common Pitfalls

### Pitfall 1: Forgetting to Register Migration in migrations.js
**What goes wrong:** The migration SQL file gets generated but the app does not apply it because `migrations.js` still only imports m0000-m0008.
**Why it happens:** `drizzle-kit generate` updates the SQL, snapshot, and journal automatically, but `migrations.js` is a manual Expo-specific registration file.
**How to avoid:** Always add the import and registration entry in `migrations.js` immediately after running `drizzle-kit generate`.
**Warning signs:** App boots successfully but new tables do not exist. Drizzle Studio shows no `machine_table` or `grinder_table`.

### Pitfall 2: Running drizzle-kit generate Before Saving Schema Changes
**What goes wrong:** Generated migration is empty or incorrect because the schema file was not saved before running the command.
**Why it happens:** `drizzle-kit generate` reads from disk, not from your editor buffer.
**How to avoid:** Save `db/schema.ts` before running `npx drizzle-kit generate`.
**Warning signs:** Generated SQL file is empty or contains unexpected statements.

### Pitfall 3: Column Name Casing Mismatch
**What goes wrong:** Drizzle uses the TypeScript property name as the column name by default. If you write `machineType` in TypeScript, the column in SQLite will be `machineType` (camelCase), not `machine_type`.
**Why it happens:** Drizzle ORM infers column names from property keys unless you pass an explicit name string.
**How to avoid:** The existing codebase uses camelCase for column names (e.g., `robustaAmount`, `arabicaAmount`, `isFavorit`). Follow the same convention. The column storing machine type should be the property name `type` in TypeScript, which produces a SQLite column named `type`.
**Warning signs:** Queries fail because the column name does not match what was expected.

### Pitfall 4: Snapshot Version Mismatch
**What goes wrong:** If you have a stale or corrupted `_journal.json`, running `drizzle-kit generate` may fail or produce an invalid migration.
**Why it happens:** The journal tracks migration indices and prev/next IDs. Manual edits can break the chain.
**How to avoid:** Never manually edit files in `drizzle/meta/`. Let `drizzle-kit generate` manage them.
**Warning signs:** `drizzle-kit generate` throws errors about missing or inconsistent snapshots.

## Open Questions

1. **Column naming for `type`**
   - What we know: The existing schema uses descriptive camelCase names (e.g., `degreeOfGrinding`, `robustaAmount`). The architecture research proposes the column name `type` for the machine type.
   - What's unclear: `type` is a reserved word in some SQL dialects but NOT in SQLite. Drizzle wraps column names in backticks in generated SQL, so `type` is safe.
   - Recommendation: Use `type` as proposed. It is concise, clear, and safe in SQLite with backtick quoting.

2. **Migration file name**
   - What we know: Drizzle-kit auto-generates a random Marvel-themed suffix (e.g., `0009_some_character.sql`). The name is not controllable without the `--name` flag.
   - What's unclear: Whether to use `--name` flag for a custom name.
   - Recommendation: Use `npx drizzle-kit generate --name add_equipment_tables` for a descriptive migration name. This is supported in drizzle-kit and makes the migration directory more readable.
